## 阶段 0：需求分析与目标设定（1-2 周）

### 目标
明确"为什么做"和"要做什么"

### 核心工作

#### 1. 明确动机和目标

**关键问题**：

**为什么要开发量化交易平台？**
- 自己交易使用？
- 学习量化技术？
- 商业化产品？
- 兴趣爱好？

**你的资金规模？**
- 1 万以下：简单策略即可
- 1-10 万：需要基础风控
- 10-100 万：需要完善系统
- 100 万以上：需要专业团队

**你的技术背景？**
- 有编程经验 vs 无编程经验
- 熟悉金融市场 vs 完全新手
- 全职开发 vs 业余时间

**输出**：明确的目标陈述

**示例**：
```
"我要开发一个个人量化交易平台，用于 A 股市场的自动化交易。
资金规模：10 万元
技术背景：Python 开发 3 年，股票交易 2 年
时间投入：业余时间，每周 10-15 小时
目标：6 个月内完成 MVP，能在模拟盘稳定运行"
```

---

#### 2. 市场和交易需求分析

**关键问题**：

**交易什么市场？**
- A 股、美股、港股、加密货币、期货？
- 不同市场的 API、交易规则、数据源完全不同

**交易什么品种？**
- 股票、ETF、可转债、期货、期权？
- 复杂品种（期权）需要更复杂的定价和风控

**交易频率？**
- 高频（秒级、毫秒级）：对延迟要求极高，个人难度大
- 日内（分钟级）：需要实时行情和快速执行
- 日线（每日调仓）：最容易实现，适合个人

**策略类型？**
- 趋势跟踪、均值回归、统计套利、因子选股？
- 不同策略对数据和计算的要求不同

**输出**：交易需求清单

**示例**：
```
- 市场：A 股主板 + 创业板
- 品种：股票（暂不涉及 ETF 和可转债）
- 频率：日线级别，每日收盘后计算信号，次日开盘执行
- 策略：因子选股 + 趋势跟踪
- 持仓：5-10 只股票，等权重或按因子值加权
```

---

#### 3. 功能优先级定义

**使用 MoSCoW 方法**：
- **Must Have（必须有）**：没有这些功能系统无法运行
- **Should Have（应该有）**：重要但不紧急，可以后续添加
- **Could Have（可以有）**：锦上添花，资源充足时做
- **Won't Have（暂不做）**：明确排除，避免范围蔓延

**示例**：
```
Must Have（MVP 必需）：
- 实时行情接收
- 策略信号生成
- 基础风控（仓位限制、止损）
- 订单执行和跟踪
- 持仓管理
- 关键告警

Should Have（第二版）：
- 回测引擎
- 因子库
- 参数优化
- 绩效分析

Could Have（可选）：
- Web 可视化界面
- 多策略并行
- 实时监控大屏

Won't Have（明确不做）：
- 高频交易
- 期权定价
- 机器学习模型训练
- 多账户管理
```

---

#### 4. 约束条件识别

**技术约束**：
- 开发语言限制（只会 Python？）
- 硬件资源（单机 vs 服务器）
- 网络环境（家庭宽带 vs 机房专线）

**资金约束**：
- 数据费用（免费 vs 付费数据源）
- 云服务费用（本地 vs 云端部署）
- 交易手续费（券商选择）

**时间约束**：
- 每周可投入时间
- 预期上线时间
- 是否有 Deadline（如准备辞职全职交易）

**合规约束**：
- 是否需要私募牌照（管理他人资金需要）
- 交易合规性（不能操纵市场、内幕交易）

**输出**：约束条件清单

---

#### 5. 成功标准定义

**定义"完成"的标准**：
- 功能完整性：核心功能都实现
- 稳定性：模拟盘运行 X 天无崩溃
- 准确性：订单状态准确率 100%
- 性能：数据延迟 < Y 秒
- 安全性：风控拦截率 100%

**定义"成功"的标准**：
- 系统层面：稳定运行 6 个月无重大事故
- 交易层面：年化收益 > 10%，最大回撤 < 20%
- 学习层面：掌握量化交易核心技术

**输出**：可衡量的成功标准

## 阶段 1：架构研究与设计（2-3 周）

### 目标

### 核心工作

#### 1. 研究对标平台（1 周）

**为什么要研究对标平台？**
- 避免重复造轮子
- 学习成熟的架构设计
- 了解常见的坑和解决方案

**研究对象**：
- **QuantConnect**：架构清晰，开源，适合学习
- **vnpy**：Python 生态，国内市场支持好
- **Backtrader**：回测框架，简单易用
- **Zipline**：Quantopian 的回测引擎

**研究方法**：

**第一步：阅读官方文档**
- 快速浏览：了解整体功能
- 重点阅读：架构设计、核心概念

**第二步：阅读源代码（选择性）**
- 不要试图读完所有代码（太大了）
- 重点看核心模块的接口设计
- 看看关键流程的实现逻辑

**第三步：运行示例**
- 跑通官方示例
- 修改示例，观察行为
- 理解关键概念（如 QuantConnect 的 OnData）

**第四步：总结优缺点**
- 列出优点（值得借鉴的）
- 列出缺点（需要改进的）
- 评估可借鉴性（适合个人开发吗？）

#### 3. 架构设计（3-5 天）

**设计你的系统架构**

**3.1 分层架构设计**
```
展示层（可选）
    ↓
应用层（策略引擎、回测引擎、实盘引擎）
    ↓
核心服务层（风控、OMS、PMS、监控告警）
    ↓
基础设施层（数据层、日志、配置）
```

**3.2 模块交互设计**
- 哪些模块之间有依赖？
- 如何解耦？（依赖注入、事件驱动）
- 如何通信？（函数调用、消息队列）

**3.3 数据流设计**
```
实时行情 → 数据清洗 → 策略计算 → 风控检查 → 
订单提交 → 成交回报 → 持仓更新
```

**3.4 技术选型**
- 编程语言：Python（快速开发） vs C#（性能）
- 数据库：PostgreSQL（时序数据） + Redis（缓存）
- 消息队列：Redis Pub/Sub（轻量） vs RabbitMQ（专业）
- 数据源：IBKR API / AKShare / Tushare
- 券商接口：IBKR / 东方财富 / 富途

### 切片 2-8：类似流程

每个切片都遵循相同的节奏：
```
启动 → 开发 → 测试 → 验收 → 演示 → 下一切片
```

**关键原则**：

**1. 完成定义明确**：什么叫"完成"？
- 功能实现
- 单元测试通过
- 集成测试通过
- 文档更新
- 代码提交

**2. 不留技术债**：
- 不要说"先实现功能，后续优化"
- 每个切片都要达到可发布质量
- 发现问题立即修复

**3. 持续集成**：
- 每天至少提交一次代码
- 每次提交都要跑测试
- 保持主分支随时可用

**4. 及时调整**：
- 发现计划不合理，立即调整
- 切片延期了，评估影响并调整后续
- 功能点无法完成，降低完成度目标

### 开发过程中的关键实践

#### 1. 测试驱动开发（TDD）
**不是必须，但强烈推荐**

```
编写测试 → 运行测试（失败）→ 编写代码 → 运行测试（通过）→ 重构
```

**特别适合的场景**：
- 风控规则（逻辑复杂，必须 100% 准确）
- 订单幂等性（防止重复下单）
- 持仓计算（金额计算必须准确）

---

#### 2. 代码审查（Code Review）
**个人开发如何做 Code Review？**

- 自我审查：提交前检查一遍代码
- 延迟审查：第二天早上再看昨天的代码
- 橡皮鸭调试：向别人（或玩偶）解释代码逻辑

---

#### 3. 文档先行
**不要等开发完再写文档**

- 设计文档：开发前写（架构设计、接口定义）
- API 文档：开发中写（函数注释、类说明）
- 用户文档：开发后写（使用手册、部署指南）

---

#### 4. 版本控制最佳实践
**Git 使用规范**

- 频繁提交：每完成一个小功能就提交
- 提交信息清晰：说明做了什么、为什么
- 使用分支：新功能在 feature 分支开发
- 保护主分支：主分支永远是稳定的

---

#### 5. 日志记录
**从第一天就要有完善的日志**

- 关键操作必须记录（订单、成交、持仓）
- 错误必须记录（异常、失败、拒绝）
- 性能指标记录（延迟、成功率）

**日志是生产环境的眼睛，没有日志就是盲人开车。**

## 阶段 5：上线与运维（持续）

### 目标
小资金上线，持续监控和优化

### 5.1 上线准备（3-5 天）

#### 1. 生产环境准备
**与开发环境隔离**

- 独立的数据库（不要用开发库）
- 独立的配置文件（生产 API Key）
- 真实的券商账户（从模拟盘切换到实盘）

#### 2. 资金准备
**小资金验证**

- 第一阶段：1000-5000 元（验证系统稳定性）
- 第二阶段：1-2 万元（验证策略有效性）
- 第三阶段：5-10 万元（正常资金量）

**原则**：
- 不要一次性投入大资金
- 亏得起的钱才能投入
- 止损线明确（如总资金 20%）

#### 3. 监控准备
**24/7 监控**

- 系统监控（CPU、内存、磁盘）
- 业务监控（订单、持仓、盈亏）
- 告警通道（邮件 + 手机短信）

#### 4. 应急预案
**出问题怎么办？**

- 系统崩溃 → 手动平仓方案
- 策略失控 → 一键停止策略
- 风控失效 → 紧急暂停所有交易
- 联系方式 → 券商客服电话

### 5.2 上线流程（1 天）

#### 上线检查清单
```
□ 生产环境配置正确（API Key、数据库连接）
□ 真实券商账户连接成功
□ 策略参数确认（仓位、止损、标的池）
□ 风控规则确认（限额、频率）
□ 监控告警测试通过
□ 应急预案准备就绪
□ 资金到账（如 5000 元）
```

#### 上线步骤
```
1. 在非交易时段（如周末）部署生产环境
2. 启动系统，但不启动策略（只接收数据）
3. 观察数据接收是否正常（1-2 小时）
4. 启动策略，但设置极小仓位（如单票 500 元）
5. 观察第一天交易（全程监控）
6. 如果正常，逐步加仓
```

### 5.3 运维阶段（持续）

#### 每日运维工作
**每天花 30-60 分钟**

**盘前（9:00 之前）**：
- 检查系统状态（是否运行正常）
- 检查数据更新（是否有最新行情）
- 检查持仓（与券商账户是否一致）
- 查看策略信号（今日是否有信号）

**盘中（9:30-15:00）**：
- 监控订单执行（是否及时成交）
- 监控持仓变化（成交后持仓是否更新）
- 监控告警（是否有异常）

**盘后（15:30 之后）**：
- 查看交易日志（今日交易明细）
- 对账（本地持仓 vs 券商持仓）
- 计算盈亏（今日盈亏、累计盈亏）
- 备份数据（交易数据、日志）
- 填写交易日记（今日反思）

### 5.5 常见问题应对

#### 问题 1：系统崩溃了怎么办？
**应急步骤**：
1. 立即手动平仓（或设置止损）
2. 停止系统，保存现场（日志、数据）
3. 排查原因（代码bug、环境问题、外部依赖）
4. 修复问题
5. 模拟盘验证修复
6. 重新上线

---

#### 问题 2：策略亏损了怎么办？
**分析逻辑**：
1. 是系统问题还是策略问题？
   - 系统问题：订单执行错误、风控失效 → 立即修复
   - 策略问题：市场环境变化、策略失效 → 评估是否继续

2. 如果是策略问题：
   - 是短期波动还是长期失效？
   - 回测和实盘是否一致？
   - 是否触及止损线？

3. 决策：
   - 继续运行（如果在正常波动范围内）
   - 暂停策略（如果连续亏损或触及止损）
   - 策略优化（如果逻辑有问题）

---

#### 问题 3：风控规则太严格，错过机会怎么办？
**平衡收益和风险**：
- 不要因为错过机会就放松风控
- 风控的目的是保护本金，不是追求收益最大化
- 如果经常被风控拦截，考虑优化策略而不是放松风控

---

#### 问题 4：市场环境变化，策略失效怎么办？
**策略生命周期管理**：
- 任何策略都有生命周期
- 定期评估策略有效性（如每季度）
- 准备多个策略应对不同市场环境
- 市场环境识别（牛市、熊市、震荡市）

---

### 关键成功因素

#### 1. 控制范围
**避免功能蔓延**

- MVP 必须小（10 个核心模块，不要更多）
- 功能边界清晰（明确不做什么）
- 抵制功能蔓延（新想法记下来，第二版再做）

**错误示例**：
- "既然做回测，不如加个参数优化器"
- "既然有数据，不如做个机器学习模型"
- "既然有订单，不如支持算法单"

**正确做法**：
- 严格对照 MVP 清单，不在清单里的不做
- 新想法记录到"第二版功能清单"
- 每周评审，砍掉不必要的功能

---

#### 2. 垂直开发
**端到端价值交付**

- 每个切片都有业务价值
- 端到端打通，及时发现问题
- 持续交付，保持动力

**好处**：
- 快速验证核心流程
- 尽早发现架构问题
- 持续的成就感

**对比水平开发**：
- 水平开发：所有模块都做到 50%，但跑不起来
- 垂直开发：50% 的功能，但完整可用

---

#### 3. 风控优先
**保护本金是第一要务**

- 宁可少做功能，风控必须到位
- 所有风控规则必须测试
- 生产环境风控更严格

**风控原则**：
- 事前检查：订单提交前拦截
- 事中监控：持仓实时监控止损
- 事后分析：异常交易检测

**反面教训**：
- "小资金不需要风控" → 一次失误亏光
- "风控太严格影响收益" → 因小失大
- "先上线，风控慢慢完善" → 第一天就出事

---

#### 4. 充分测试
**测试永远不嫌多**

- 关键路径必须测试（订单、持仓、风控）
- 模拟盘长稳测试（至少 7 天）
- 小资金验证（1000-5000 元）

**测试层次**：
1. 单元测试：每个函数都正确
2. 集成测试：模块间协作正确
3. 系统测试：端到端流程正确
4. 压力测试：极端情况不崩溃
5. 长稳测试：长时间运行稳定

**测试覆盖率目标**：
- 风控规则：100%
- 订单管理：100%
- 持仓计算：100%
- 其他模块：> 80%

#### 5. 持续学习
**量化交易是终身学习的领域**

- 记录交易日记
- 总结经验教训
- 持续优化系统和策略

**学习内容**：
- 技术层面：新技术、新框架、性能优化
- 策略层面：新因子、新模型、市场规律

### 常见失败原因

#### ❌ 失败原因 1：过度工程化
**表现**：
- 想一次做完美系统
- 功能太多，永远做不完
- 追求技术先进性，忽略业务价值

**后果**：
- 开发 6 个月还没做完
- 做出来的东西太复杂，自己都不会用
- 失去耐心，半途而废

**避免方法**：
- 严格控制 MVP 范围
- 功能优先级清晰（MoSCoW 方法）
- 每个功能都问：不做会死吗？

---

#### ❌ 失败原因 2：轻视风控
**表现**：
- 觉得小资金不需要风控
- 风控规则不完善
- 为了收益放松风控

**后果**：
- 一次事故亏光本金
- 订单重复下单，双倍亏损
- 策略失控，连续亏损不止损

**避免方法**：
- 风控从第一天就做
- 所有风控规则单元测试 100%
- 生产环境风控比模拟盘更严

---

#### ❌ 失败原因 3：跳过测试
**表现**：
- 急于上线，跳过测试阶段
- 没有模拟盘验证
- 测试不充分就上真实资金

**后果**：
- 生产环境频繁出问题
- 订单状态不准确
- 持仓对账发现差异

**避免方法**：
- 模拟盘至少运行 7 天
- 4 个关键风险点必须验证
- 小资金验证（1000-5000 元）

---

#### ❌ 失败原因 4：没有止损
**表现**：
- 策略亏损不愿承认
- 期待"回本"
- 不断加仓摊低成本

**后果**：
- 小亏变大亏
- 本金损失过半
- 影响心态，更难理性决策

**避免方法**：
- 明确止损线（如总资金 20%）
- 自动止损（系统强制执行）
- 定期评估策略有效性

---

#### ❌ 失败原因 5：孤军奋战
**表现**：
- 遇到问题不寻求帮助
- 没有社区支持
- 闭门造车

**后果**：
- 走很多弯路
- 重复踩坑
- 缺乏动力，容易放弃

**避免方法**：
- 加入量化社区（聚宽、米筐）
- 阅读开源项目代码
- 找量化交易的朋友交流

## 最后的建议

### 1. 不要追求完美
> **"完成比完美更重要"**
> 
> MVP 的目标是验证想法，不是做出完美产品。
> 
> 先做出能用的，再慢慢优化。

---

### 2. 保持耐心
> **"量化交易是马拉松，不是百米冲刺"**
> 
> 4-6 个月才能上线，这是正常的。
> 
> 不要因为进度慢就气馁，这是复杂系统。

---

### 3. 享受过程
> **"如果不享受开发过程，很难坚持到最后"**
> 
> 把它当作学习和探索，而不只是赚钱工具。
> 
> 每个切片完成后，停下来欣赏一下自己的成果。

---

### 4. 控制风险
> **"保护本金是第一要务"**
> 
> 小资金验证，严格风控，逐步加仓。
> 
> 亏得起的钱才能投入实盘。

---

### 5. 持续学习
> **"市场一直在变，你也要一直学习"**
> 
> 技术、策略、市场，都需要持续学习。
> 
> 记录每一次交易，总结每一次失败。
