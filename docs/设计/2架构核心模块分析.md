## 二、核心模块详解

### 2.1 数据层（Data Layer）

**职责**：系统的数据基础设施

#### 2.1.1 子模块
- **数据采集**：爬虫、API 接入、数据供应商对接
- **数据存储**：时序数据库、行情数据、财务数据、另类数据
- **数据清洗**：缺失值处理、异常值检测、复权处理
- **数据服务**：统一查询接口、数据缓存、订阅分发

#### 2.1.2 关键设计点
- **数据存储策略**
  - 分钟级数据：PostgreSQL/TimescaleDB（用于回测和复盘）
  - Tick 级数据：仅在高频交易时需要
  - 实时数据：Redis 缓存最新 N 根 K 线
  
- **数据质量保证**
  - 异常值检测（价格突变、成交量异常）
  - 缺失数据补全策略
  - 复权处理（前复权、后复权）

#### 2.1.3 个人开发建议
- ✅ **高优先级**：必需的基础设施
- 建议使用成熟数据源（AKShare、Tushare、IBKR API）
- 不要过早优化存储，初期单机数据库即可

### 2.2 策略引擎（Strategy Engine）

**职责**：策略逻辑的执行容器

#### 2.2.1 核心功能
- 加载和初始化策略代码
- 管理策略生命周期（启动、暂停、停止）
- 调度策略的回调函数（`OnData`、`OnOrder`、`OnTimer` 等）
- 提供策略 API（下单、查询持仓、获取数据等）
- 隔离策略运行环境（沙箱、资源限制）

#### 2.2.2 策略生命周期
```
[策略加载]
    ↓
Initialize()  - 策略初始化（加载参数、订阅数据）
    ↓
OnData()      - 接收新数据时触发
    ↓
OnOrder()     - 订单状态变化时触发
    ↓
OnEndOfDay()  - 交易日结束时触发
    ↓
OnShutdown()  - 策略停止时触发
```

#### 2.2.3 策略 API 设计
```python
# 策略基类示例（伪代码）
class Strategy:
    def Buy(symbol, quantity, order_type='Market')
    def Sell(symbol, quantity, order_type='Market')
    def GetHolding(symbol) -> Position
    def GetHistoricalData(symbol, period) -> DataFrame
    def Log(message)
    def SetStopLoss(symbol, price)
```

#### 2.2.4 关键点
**策略引擎本身不关心是回测还是实盘，它只负责"运行策略代码"。**

通过依赖注入，策略引擎可以在不同环境中运行：
- 回测环境：注入历史数据源 + 模拟交易接口
- 实盘环境：注入实时数据源 + 真实交易接口

#### 2.2.5 个人开发建议
- ✅ **高优先级**：核心中的核心
- 采用事件驱动架构
- 提供清晰的策略模板和示例

### 2.3 回测引擎（Backtest Engine）

**职责**：模拟历史市场环境

#### 2.3.1 核心功能
- **时间驱动**：按历史时间顺序推进
- **模拟撮合**：根据历史行情模拟订单成交
- **模拟账户**：计算持仓、可用资金、盈亏
- **滑点模型**：模拟真实交易的成交偏差
- **手续费模型**：计算交易成本
- **绩效分析**：计算夏普比率、最大回撤等指标

#### 2.3.2 回测模式
1. **事件驱动回测**
   - 按时间顺序逐条处理数据
   - 模拟真实交易流程
   - 准确但速度慢

2. **向量化回测**
   - 批量计算信号和收益
   - 速度快但精度较低
   - 适合快速验证想法

#### 2.3.3 成交模拟策略
- **市价单**：下一个 Bar 的开盘价成交（假设无滑点）
- **限价单**：价格触及限价时成交
- **高级模拟**：考虑成交量限制、价格冲击

#### 2.3.4 个人开发建议
- ✅ **高优先级**：策略验证必需
- 初期实现简单的事件驱动回测
- 后期可添加更精细的成交模拟

### 2.4 实盘交易引擎（Live Trading Engine）

**职责**：真实市场环境下执行交易

#### 2.4.1 核心功能
- **实时数据接入**：WebSocket/UDP 行情订阅
- **券商对接**：下单、撤单、查询 API
- **订单路由**：选择最优通道下单
- **订单管理**：跟踪订单状态、部分成交处理
- **异常处理**：断线重连、订单恢复、故障转移
- **延迟监控**：从信号产生到下单的时延统计

#### 2.4.2 实时数据处理
```
[实时行情推送]
    ↓
数据验证（时间戳、价格合理性）
    ↓
更新缓存（Redis）
    ↓
触发策略回调
    ↓
生成交易信号
    ↓
风控检查
    ↓
下单执行
```

#### 2.4.3 断线重连机制
```
检测到连接断开
    ↓
停止新订单提交
    ↓
保存当前状态快照
    ↓
自动重连（指数退避）
    ├─ 尝试1: 立即重连
    ├─ 尝试2: 5秒后
    ├─ 尝试3: 15秒后
    └─ 超过N次 → 告警通知
    ↓
重连成功 → 状态恢复
```

#### 2.4.4 个人开发建议
- ✅ **高优先级**：实盘必需
- 重点关注异常处理和容错
- 充分测试各种异常场景

### 2.5 策略引擎 vs 回测引擎：核心区别

#### 2.5.1 关系图
```
┌─────────────────────────────────────┐
│          策略引擎 (核心)              │
│   - 运行策略代码                     │
│   - 管理策略生命周期                 │
│   - 提供策略 API                     │
└──────────┬─────────────┬────────────┘
           │             │
    ┌──────▼─────┐  ┌────▼──────────┐
    │ 回测引擎    │  │ 实盘引擎       │
    │ - 历史数据  │  │ - 实时数据     │
    │ - 模拟账户  │  │ - 真实下单     │
    │ - 模拟成交  │  │ - 订单跟踪     │
    └────────────┘  └───────────────┘
```

#### 2.5.2 本质区别
- **策略引擎**：策略代码的**运行时容器**，负责调度和 API 提供
- **回测引擎**：历史市场的**模拟器**，提供历史数据和模拟交易环境
- **实盘引擎**：真实市场的**连接器**，提供实时数据和真实交易能力

#### 2.5.3 关系总结
```
策略引擎 + 回测数据环境 = 回测引擎
策略引擎 + 实盘数据环境 = 实盘引擎
```

#### 2.5.4 为什么要分离？

**1. 统一代码路径**
- 同一套策略代码可以无缝切换回测和实盘
- 策略只调用抽象接口（如 `Buy()`），不关心底层实现

**2. 可替换性**
- 可以实现多种回测模式（事件驱动、向量化）
- 可以对接不同券商（接口统一）

**3. 职责清晰**
- 策略引擎专注策略逻辑执行
- 回测引擎专注模拟准确性
- 实盘引擎专注交易可靠性

#### 2.5.5 依赖注入设计
```python
# 伪代码示例
class StrategyEngine:
    def __init__(self, data_provider: IDataProvider, broker: IBroker):
        self.data = data_provider
        self.broker = broker
    
    def run_strategy(self, strategy):
        # 策略执行逻辑
        data = self.data.get_latest()
        signal = strategy.on_data(data)
        if signal:
            self.broker.place_order(signal)

# 回测模式
backtest_engine = StrategyEngine(
    data_provider=HistoricalDataProvider(),
    broker=SimulatedBroker()
)

# 实盘模式
live_engine = StrategyEngine(
    data_provider=LiveDataProvider(),
    broker=RealBroker()  # 连接券商 API
)
```

### 2.6 风控引擎（Risk Management Engine）

**重要性**：★★★★★（生产环境必需）

#### 2.6.1 风控层级

**事前风控（下单前检查）**
- 单笔订单金额限制
- 持仓集中度控制（单票不超过总资产 20%）
- 杠杆率限制
- 禁止开仓标的黑名单
- 交易时段检查

**事中风控（持仓监控）**
- 实时盈亏跟踪
- 止损/止盈触发
- 保证金不足预警
- 当日亏损限制（达到 2% 停止开仓）

**事后风控（绩效评估）**
- 日内最大回撤监控
- 异常交易检测
- 合规性检查（如 T+1、涨跌停）

#### 2.6.2 风控规则示例
```python
# 伪代码
class RiskRule:
    def check_single_position_limit(position_value, total_capital):
        """单个股票持仓不超过总资产 20%"""
        return position_value / total_capital <= 0.20
    
    def check_daily_loss_limit(daily_pnl, total_capital):
        """单日亏损不超过总资产 2%"""
        return abs(daily_pnl) / total_capital <= 0.02
    
    def check_trade_frequency(trade_count_today, max_trades=100):
        """单日交易次数限制"""
        return trade_count_today < max_trades
```

#### 2.6.3 个人开发建议
- ✅ **最高优先级**：保护资金安全
- 采用"白名单"思维：默认拒绝，明确允许
- 所有风控规则必须有单元测试

### 2.7 订单管理系统（Order Management System - OMS）

**重要性**：★★★★★（实盘必需）

#### 2.7.1 订单生命周期
```
[创建订单]
    ↓
[提交到券商] → PreSubmitted
    ↓
[券商确认] → Submitted
    ↓
[开始成交] → PartiallyFilled
    ↓
[全部成交] → Filled
    
[取消路径]
    → Cancelling → Cancelled
    
[拒绝路径]
    → Rejected
```

#### 2.7.2 订单类型支持
- **基础订单**
  - 市价单（Market）
  - 限价单（Limit）
  
- **高级订单**（第二阶段）
  - 止损单（Stop）
  - 止盈单（Take Profit）
  - 条件单（Conditional）
  - 算法单（VWAP、TWAP）

#### 2.7.3 订单幂等性设计
防止重复下单的关键机制：
```python
# 订单唯一标识
order_id = f"{strategy_id}_{symbol}_{timestamp}_{signal_hash}"

# 60秒内相同信号去重
if redis.exists(f"order_lock:{order_id}"):
    return "订单已存在，跳过"
    
redis.setex(f"order_lock:{order_id}", 60, "1")
```

#### 2.7.4 个人开发建议
- ✅ **高优先级**：实盘核心
- 订单状态机必须严格测试
- 重点关注订单幂等性

### 2.8 仓位管理系统（Portfolio Management System - PMS）

**重要性**：★★★★☆

#### 2.8.1 核心功能
- **持仓核算**
  - 实时持仓数量、成本、市值
  - 可用资金计算
  - 冻结资金管理
  
- **盈亏计算**
  - 浮动盈亏（Unrealized PnL）= (当前价格 - 成本价) × 持仓量
  - 已实现盈亏（Realized PnL）= 平仓收益
  - 日内盈亏、累计盈亏
  
- **绩效归因**
  - 收益来源分析（选股、择时、行业配置）
  - 风险分解（市场风险、特定风险）

#### 2.8.2 持仓对账机制
```
定时任务（每5分钟）
    ↓
从券商拉取持仓快照
    ↓
对比本地持仓记录
    ↓
差异检测
    ├─ 差异 < 1股 → 正常
    └─ 差异 >= 1股 → 告警
```

#### 2.8.3 个人开发建议
- ✅ **高优先级**：资金核算基础
- 持仓数据以券商为权威源
- 定期对账机制必须实现

- **基本面因子**

  - 资金流因子

#### 2.9.2 因子计算框架
```python
# 因子基类（伪代码）
class Factor:
    def __init__(self, window_size):
        self.window = window_size
    
    def calculate(self, data: DataFrame) -> Series:
        """计算因子值"""
        pass

class MomentumFactor(Factor):
```

## 四、架构设计最佳实践

### 4.1 设计原则

**1. 关注点分离**
- 每个模块职责单一
- 模块间通过接口通信
- 避免循环依赖

**2. 依赖注入**
- 策略引擎不直接依赖具体实现
- 通过接口注入数据源和交易接口
- 便于测试和切换环境

**3. 事件驱动**
- 使用消息队列解耦模块
- 异步处理非关键路径
- 提高系统响应性

**4. 防御式编程**
- 所有外部输入必须验证
- 关键操作必须有日志
- 异常必须妥善处理

**单元测试**

## 五、常见问题与解答

### Q1：策略引擎和回测引擎必须分离吗？
**A**：不是必须，但强烈建议。分离后同一套策略代码可无缝切换回测和实盘，大大降低维护成本。

### Q2：个人开发需要实现所有模块吗？
**A**：不需要。MVP 阶段只需 5 个核心模块：数据层、策略引擎、回测引擎、基础风控、日志系统。其他模块按需逐步添加。

### Q3：数据层需要支持多数据源吗？
**A**：初期不需要。选择一个稳定的数据源（如 IBKR API）即可。后期可扩展。

### Q4：风控引擎应该放在哪个环节？
**A**：至少两个环节：
1. **前置检查**（订单提交前）：必须，拒绝不合规订单
2. **持续监控**（运行时）：必须，监控止损止盈

### Q5：如何避免过度工程化？
**A**：遵循"能用就行"原则：
- 不要一开始就追求完美架构
- 先实现核心功能，后优化
- 根据实际痛点迭代
