# 个人量化交易系统架构设计文档 v1.0

**文档版本**：v1.0  
**创建日期**：2026-08-17  
**文档状态**：✅ 权威版本  
**适用范围**：个人量化交易系统

---

## 一、系统定位

- **目的**：长期使用的个人交易系统
- **投入**：每周 25-30 小时（半全职）
- **要求**：7×24 稳定运行
- **范围**：美股交易，IBKR 券商，PostgreSQL 存储

---

## 二、开发策略

### 核心原则

1. **实盘优先**：先做实盘交易能力，再补回测
2. **渐进式开发**：每周交付可运行的功能
3. **稳定性优先**：必须实现容错和监控
4. **避免过度设计**：个人使用，够用即可

### 为什么实盘优先？

**理由**：
- 回测可以离线慢慢做，实盘能力是刚需
- 实盘倒逼你把基础设施做扎实（连接、订单、持仓、监控）
- 先有实盘能力，可以小额验证策略
- 回测引擎可以复用实盘的数据层和策略层

## 三、系统架构设计

### 3.1 整体分层架构

```
┌─────────────────────────────────────────────────────┐
│                   应用层                             │
├──────────────┬──────────────┬──────────────────────┤
│  策略引擎    │  回测引擎     │  实盘交易引擎         │
└──────┬───────┴──────┬───────┴──────┬───────────────┘
       │              │              │
┌──────▼──────────────▼──────────────▼───────────────┐
│                   核心服务层                         │
├──────────────┬──────────────┬──────────────────────┤
│  风控引擎    │  订单管理(OMS)│  仓位管理(PMS)        │
└──────┬───────┴──────┬───────┴──────┬───────────────┘
       │              │              │
┌──────▼──────────────▼──────────────▼───────────────┐
│                   基础设施层                         │
├──────────────┬──────────────┬──────────────────────┤
│  数据层      │  消息队列     │  日志审计             │
│  (时序数据库) │  (Redis)     │  配置管理             │
└──────────────┴──────────────┴──────────────────────┘
```

### 3.2 核心模块职责

#### Algorithm Layer（策略层）

**QCAlgorithm 基类**：

- **生命周期方法**
  - Initialize：初始化策略参数、订阅标的
  - OnData：数据到达回调
  - OnOrderEvent：订单状态变更回调
  
- **交易 API**
  - AddEquity：订阅股票
  - MarketOrder：市价单
  - LimitOrder：限价单
  - StopMarketOrder：止损单
  
- **查询 API**
  - Portfolio：持仓查询
  - Account：账户查询
  - Securities：标的信息

- **技术指标 API**
  - SMA、EMA、RSI、MACD、BB
  - 自动预热和更新

**特点**：回测和实盘代码完全一致，通过 Mode 参数区分运行模式

#### Engine Layer（引擎层）

**Live Trading Engine（实盘引擎）**：

- 实时数据处理器：从 IBKR 接收实时数据，标准化格式，推送给策略
- 订单路由器：接收策略信号，风控检查，提交到 IBKR，订单状态跟踪
- 状态同步器：定时同步持仓（每分钟），订单状态同步，账户资金同步
- 断线重连：连接检测，自动重连，状态恢复

**Backtesting Engine（回测引擎）**：

- 时间管理器：按时间戳遍历历史数据，跳过非交易日，支持日线和分钟线
- 订单模拟器：市价单/限价单成交模拟，手续费计算，固定滑点模型
- 绩效计算器：实时计算权益曲线，回撤、夏普比率等指标

#### Data Layer（数据层）

**实时数据**：
- IBKR 实时订阅：通过 ib_insync 订阅，支持 5秒 Bar 和 Tick
- 数据缓存（Redis）：缓存最新价格，5 分钟 TTL

**历史数据**：
- 数据下载：IBKR 历史数据 API，yfinance 备用，断点续传，数据质量检查
- 数据存储（PostgreSQL）：
  - bars 表：symbol、timestamp、resolution、open、high、low、close、volume
  - securities 表：symbol、name、exchange、sector、industry、market_cap

#### Brokerage Layer（券商层）

**IBKR 适配器**：

- 连接管理：连接 TWS / Gateway，连接状态监控，自动重连
- 订单执行：place_order、cancel_order、modify_order
- 查询接口：get_positions、get_account_balance、get_open_orders
- 状态回调：订单状态变更，成交通知，错误通知

#### Infrastructure Layer（基础设施层）

**数据库（PostgreSQL）**：
- market_data：历史行情
- trading：订单、持仓
- backtest：回测结果

**缓存（Redis，可选）**：
- 实时行情缓存
- 策略状态缓存

**日志与监控（Loguru）**：
- 结构化日志，按天轮转，保留 30 天

**监控告警**：
- 5 级告警（P0-Critical 到 P4-Info）
- 告警去重：5 分钟内相同告警合并
- 监控指标：IBKR 连接状态，系统资源，策略运行状态，订单执行情况

## 四、架构简化策略

| 维度 | 企业版 | 个人版 | 简化理由 |
|------|--------|--------|----------|
| **券商接入** | 多券商插件化 | 仅 IBKR | 个人账户只需一个券商 |
| **数据源** | 多数据源聚合 | IBKR + yfinance 备用 | IBKR 提供实时和历史数据 |
| **消息队列** | Kafka/RabbitMQ | Redis Pub/Sub | 单机部署，Redis 足够 |
| **数据库** | 分布式集群 | PostgreSQL 单机 | 数据量小，单机即可 |
| **高可用** | 多节点冗余 | 单进程 + 日志监控 | 个人可接受短暂中断 |
| **用户系统** | 多租户隔离 | 无 | 仅自己使用 |

## 五、核心业务流程

### 实盘交易主循环

```
1. 数据输入层
   ↓
2. 数据处理层（清洗、指标计算、缓存更新）
   ↓
3. 策略执行层（触发策略计算，生成交易信号）
   ↓
4. 风控检查层（资金检查、持仓限额、交易频率、市场状态）
   ↓
5. 订单生成层（计算目标仓位、选择订单类型）
   ↓
6. 订单执行层（提交订单到 IBKR，保存到数据库）
   ↓
7. 订单跟踪层（异步监听状态变化，更新持仓）
   ↓
8. 持仓管理层（更新持仓数据，计算盈亏，对账）
   ↓
9. 监控告警层（账户监控、异常检测、触发告警）
```

### 系统启动/恢复流程

```
系统启动
  ↓
加载配置
  ↓
初始化数据库连接
  ↓
连接 IBKR（失败重试3次）
  ↓
状态恢复（从 IBKR 拉取持仓、未完成订单，对比本地数据）
  ↓
订阅市场数据
  ↓
启动策略调度器
  ↓
启动监控守护进程
  ↓
进入主循环
```

## 六、关键技术决策

### 决策 1：为什么实盘优先？

**传统路线**：回测 → 模拟盘 → 实盘  
**本方案**：实盘能力 → 回测 → 优化

**理由**：回测可以慢慢做，实盘是核心能力；实盘倒逼基础设施做扎实

### 决策 2：为什么选 PostgreSQL 而非 SQLite？

**理由**：需要 7×24 稳定运行，并发性能重要；数据量会持续增长；后期可安装 TimescaleDB 插件

### 决策 3：Redis 是否必须？

**结论**：可选，不是必须

**不用 Redis 的替代方案**：实时价格直接从 IBKR 获取，策略状态保存在内存，启动时从数据库恢复

### 决策 4：是否需要多策略进程隔离？

**阶段 1-3**：不需要，单进程多策略足够

### 决策 5：监控告警的优先级

**必须有（Week 2）**：IBKR 连接断开、订单被拒绝、系统崩溃  
**应该有（Week 4）**：系统资源超限、数据质量异常  
**可以有（Week 8）**：语音告警、监控大屏

## 七、明确不做的功能

### 回测方面
- ❌ Tick 级别回测
- ❌ 多时间周期同时回测
- ❌ 复杂滑点模型（仅固定滑点）
- ❌ 部分成交模拟
- ❌ 期权期货

### 实盘方面
- ❌ 多券商支持（仅 IBKR）
- ❌ 多账户管理
- ❌ 高频交易（秒级）
- ❌ 策略进程隔离（阶段 1-3 不做）
- ❌ 在线策略编辑器

### 基础设施
- ❌ TimescaleDB（PostgreSQL 足够）
- ❌ Prometheus + Grafana（成本高）
- ❌ Docker 容器化（增加复杂度）
- ❌ CI/CD 自动化（手动部署足够）
- ❌ 分布式架构

## 八、风险评估与应对

| 风险 | 等级 | 影响 | 应对措施 |
|------|------|------|----------|
| IBKR 连接不稳定 | 高 | 实盘中断 | Week 2 实现断线重连 + 告警 |
| 策略 Bug 导致异常交易 | 高 | 资金损失 | 充分回测 + 模拟盘验证 + 风控 |
| 数据质量问题 | 中 | 回测失真 | Week 4 实现数据质量检查 |
| 时间投入不足 | 中 | 进度延期 | 每周独立交付，可调整优先级 |
| 系统性能不足 | 低 | 策略数量受限 | Week 8 性能优化 |
