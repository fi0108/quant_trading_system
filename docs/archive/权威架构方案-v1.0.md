# 个人量化交易系统权威架构方案 v1.0

## 系统定位

- **目的**：长期使用的个人交易系统
- **投入**：每周 25-30 小时（半全职）
- **要求**：7×24 稳定运行
- **范围**：美股交易，IBKR 券商，PostgreSQL 存储

---

## 开发策略

### 核心原则

1. **实盘优先**：先做实盘交易能力，再补回测
2. **渐进式开发**：每周交付可运行的功能
3. **稳定性优先**：必须实现容错和监控
4. **避免过度设计**：个人使用，够用即可

### 为什么实盘优先？

**理由**：
- 回测可以离线慢慢做，实盘能力是刚需
- 实盘倒逼你把基础设施做扎实（连接、订单、持仓、监控）
- 先有实盘能力，可以小额验证策略
- 回测引擎可以复用实盘的数据层和策略层

**目标**：能在 IBKR 模拟盘稳定运行简单策略

**交付标准**：在纸盘下出第一个订单并成交

**必须实现**：
- IBKR 连接和实时数据订阅（8小时）
  - 连接 IBKR Gateway
  - 订阅单个标的（AAPL）5秒 Bar
  - 数据推送到策略
  
- 固定买入策略（2小时）
  - 每收到 10 次数据买入 1 股
  - 不看价格、不看持仓
  
- 订单管理（5小时）
  - 接收信号创建市价单
  - 提交到 IBKR
  - 打印订单 ID
  
- 基础风控（3小时）

  - 不足则拒绝下单
  
- 持仓查询（3小时）

  - 打印持仓列表
  
- 日志记录（2小时）

- 集成测试（2小时）

## 架构分层设计（最终形态）

### 1. Algorithm Layer（策略层）

**QCAlgorithm 基类**：

- **生命周期方法**
  - Initialize：初始化策略参数、订阅标的
  - OnData：数据到达回调
  - OnOrderEvent：订单状态变更回调
  
- **交易 API**
  - AddEquity：订阅股票
  - MarketOrder：市价单
  - LimitOrder：限价单
  - StopMarketOrder：止损单
  
- **查询 API**
  - Portfolio：持仓查询
  - Account：账户查询
  - Securities：标的信息

- **技术指标 API**
  - SMA、EMA、RSI、MACD、BB
  - 自动预热和更新

**特点**：
- 回测和实盘代码完全一致
- 通过 Mode 参数区分运行模式

---

### 2. Engine Layer（引擎层）

#### 2.1 Live Trading Engine（实盘引擎）

**核心组件**：

- **实时数据处理器**
  - 从 IBKR 接收实时数据
  - 标准化数据格式
  - 推送给策略

- **订单路由器**
  - 接收策略信号
  - 风控检查
  - 提交到 IBKR
  - 订单状态跟踪

- **状态同步器**
  - 定时同步持仓（每分钟）
  - 订单状态同步
  - 账户资金同步

- **断线重连**
  - 连接检测
  - 自动重连
  - 状态恢复

#### 2.2 Backtesting Engine（回测引擎）

**核心组件**：

- **时间管理器**
  - 按时间戳遍历历史数据
  - 跳过非交易日
  - 支持日线和分钟线

- **订单模拟器**
  - 市价单成交模拟
  - 限价单成交模拟
  - 手续费计算
  - 固定滑点模型

- **绩效计算器**
  - 实时计算权益曲线
  - 回撤、夏普比率等指标

---

### 3. Data Layer（数据层）

#### 3.1 实时数据

**IBKR 实时订阅**：
- 通过 ib_insync 订阅
- 支持 5秒 Bar 和 Tick
- 断线重连后自动重新订阅

**数据缓存（Redis，可选）**：
- 缓存最新价格
- 5 分钟 TTL

#### 3.2 历史数据

**数据下载**：
- IBKR 历史数据 API
- yfinance 备用
- 断点续传
- 数据质量检查

**数据存储（PostgreSQL）**：

**bars 表**：
- symbol、timestamp、resolution
- open、high、low、close、volume
- 索引：(symbol, timestamp, resolution)

**securities 表**：
- symbol、name、exchange
- sector、industry、market_cap

---

### 4. Brokerage Layer（券商层）

**IBKR 适配器**：

- **连接管理**
  - 连接 TWS / Gateway
  - 连接状态监控
  - 自动重连

- **订单执行**
  - 下单：place_order
  - 撤单：cancel_order
  - 改单：modify_order

- **查询接口**
  - 持仓：get_positions
  - 账户：get_account_balance
  - 订单：get_open_orders

- **状态回调**
  - 订单状态变更
  - 成交通知
  - 错误通知

---

### 5. Infrastructure Layer（基础设施层）

#### 5.1 数据库（PostgreSQL）

**数据库划分**：
- market_data：历史行情
- trading：订单、持仓
- backtest：回测结果

#### 5.2 缓存（Redis，可选）

**用途**：
- 实时行情缓存
- 策略状态缓存

#### 5.3 日志与监控

**Loguru 日志**：
- 结构化日志
- 按天轮转
- 保留 30 天

**监控告警**：

**5 级告警**：
- P0-Critical：语音电话（可选）+ 短信 + 邮件
- P1-High：短信 + 邮件
- P2-Medium：邮件
- P3-Low：邮件（非紧急）
- P4-Info：日志

**告警去重**：
- 5 分钟内相同告警合并

**监控指标**：
- IBKR 连接状态
- 系统资源（CPU、内存、磁盘）
- 策略运行状态
- 订单执行情况
- 数据质量

## 关键技术决策

### 决策 1：为什么实盘优先？

**传统路线**：回测 → 模拟盘 → 实盘
**本方案**：实盘能力 → 回测 → 优化

**理由**：
- 回测可以慢慢做，实盘是核心能力
- 实盘倒逼基础设施做扎实
- 可以边做实盘边验证策略想法
- 回测复用实盘的代码和架构

### 决策 2：为什么选 PostgreSQL 而非 SQLite？

**理由**：
- 需要 7×24 稳定运行，并发性能重要
- 数据量会持续增长
- 支持更丰富的查询和索引优化
- 后期可直接安装 TimescaleDB 插件

### 决策 3：Redis 是否必须？

**结论**：可选，不是必须

**不用 Redis 的替代方案**：
- 实时价格直接从 IBKR 获取
- 策略状态保存在内存
- 启动时从数据库恢复

**用 Redis 的好处**：
- 行情缓存可以跨策略共享
- 降低 IBKR 查询频率
- 更快的数据访问

**建议**：Week 1-4 不用，后续按需加入

### 决策 4：是否需要多策略进程隔离？

**阶段 1-3**：不需要
- 单进程多策略足够
- 简化架构和通信

**阶段 4 后**：按需评估
- 如果策略数量 > 5 个，考虑隔离
- 如果单个策略占用资源过高，考虑隔离

### 决策 5：监控告警的优先级

**必须有（Week 2）**：
- IBKR 连接断开
- 订单被拒绝
- 系统崩溃

**应该有（Week 4）**：
- 系统资源超限
- 数据质量异常
- 单日亏损超阈值

**可以有（Week 8）**：
- 语音告警（P0 级别）
- 告警统计分析
- 监控大屏
