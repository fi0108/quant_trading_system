## 文档说明

本文档从完整的量化交易系统架构中，提炼出 **MVP（最小可行产品）** 版本的核心模块清单。

**设计理念**：聚焦核心交易路径，确保"能稳定运行、能安全交易"，避免过度工程化。

**模块划分**：5+5 模型
- **第一阶段（5 个模块）**：基础框架，支持回测验证
- **第二阶段（5 个模块）**：实盘能力，支持真实交易

## 一、MVP 核心模块（5+5 模型）

### 🎯 第一阶段：基础框架（4-6 周）

#### 模块 1：数据层（Data Layer）
**优先级**：P0  
**时间估算**：1-2 周

##### 核心功能
- ✅ 实时行情订阅（IBKR API / WebSocket）
- ✅ 历史数据存储（PostgreSQL / TimescaleDB）
- ✅ Redis 缓存最新 100 根 K 线（策略快速访问）
- ✅ 基础数据清洗（异常值检测、缺失值处理）

##### 技术选型
```
数据库：PostgreSQL 或 TimescaleDB
缓存：Redis
数据接口：IBKR API / AKShare / Tushare
```

##### 验收标准
- ✅ 能稳定接收实时行情 24 小时不断线
- ✅ 数据完整无丢失
- ✅ 数据延迟 < 1 秒

##### MVP 边界（不做）
- ❌ Tick 级数据存储（除非做高频）
- ❌ 多数据源聚合和切换
- ❌ 复杂的数据清洗逻辑（ML 去噪等）
- ❌ 数据质量评分系统

##### 关键风险
- 数据源 API 稳定性问题 → 需要心跳检测和重连机制

#### 模块 2：策略引擎（Strategy Engine）
**优先级**：P0  
**时间估算**：1-2 周

##### 核心功能
- ✅ 策略加载和初始化
- ✅ 生命周期管理
  - `Initialize()` - 策略初始化
  - `OnData()` - 接收新数据时触发
  - `OnEndOfDay()` - 交易日结束时触发
- ✅ 提供策略 API
  - `Buy(symbol, quantity)` - 买入
  - `Sell(symbol, quantity)` - 卖出
  - `GetHolding(symbol)` - 查询持仓
  - `GetHistoricalData(symbol, period)` - 获取历史数据
- ✅ 事件驱动调度

##### 策略生命周期示例
```python
class MyStrategy(Strategy):
    def Initialize(self):
        """策略初始化"""
        self.symbol = "AAPL"
        self.Subscribe(self.symbol)
    
    def OnData(self, data):
        """接收新数据"""
        if self.should_buy():
            self.Buy(self.symbol, 100)
    
    def OnEndOfDay(self):
        """交易日结束"""
        self.Log(f"Today PnL: {self.GetDailyPnL()}")
```

##### 验收标准
- ✅ 支持 2-3 个简单策略（均线交叉、网格策略、固定仓位）
- ✅ 策略信号生成正确
- ✅ 策略间隔离（一个策略崩溃不影响其他）

##### MVP 边界（不做）
- ❌ 多策略并行执行（初期只运行 1-2 个策略）
- ❌ 策略热更新（需要重启系统）
- ❌ 复杂的沙箱隔离（资源限制、安全隔离）
- ❌ 策略版本管理

##### 关键设计
- **依赖注入**：策略不直接依赖数据源和交易接口，通过接口注入

#### 模块 3：回测引擎（Backtest Engine）
**优先级**：P0  
**时间估算**：1-2 周

##### 核心功能
- ✅ 简单的事件驱动回测（按时间顺序逐条处理数据）
- ✅ 基础成交模拟
  - 市价单：下一 Bar 的开盘价成交
  - 限价单：价格触及限价时成交
- ✅ 固定手续费模型（如万分之五）
- ✅ 基础绩效指标
  - 累计收益率
  - 最大回撤
  - 胜率
  - 交易次数

##### 回测流程
```
加载历史数据
    ↓
初始化策略
    ↓
按时间顺序遍历数据
    ├─ 触发策略 OnData()
    ├─ 生成交易信号
    ├─ 模拟成交
    └─ 更新持仓和资金
    ↓
计算绩效指标
    ↓
输出回测报告
```

##### 验收标准
- ✅ 完成日线级别简单策略回测
- ✅ 回测结果可视化（收益曲线图）
- ✅ 回测时间合理（1 年数据 < 10 秒）

##### MVP 边界（不做）
- ❌ 复杂滑点模型（价格冲击、流动性影响）
- ❌ 高频 Tick 级回测
- ❌ 参数优化器（网格搜索、遗传算法）
- ❌ Walk-Forward 分析
- ❌ 向量化回测（初期事件驱动即可）

##### 关键注意
- **避免未来数据泄露**：确保策略只能访问当前时间点之前的数据

#### 模块 4：基础风控（Basic Risk Management）
**优先级**：P0  
**时间估算**：1 周

##### 核心功能：前置检查（订单提交前）

```python
# 风控规则
1. 资金充足性检查
   - 可用资金 >= 订单金额 × 1.1（预留 10% 缓冲）

2. 单票持仓限制
   - 单个股票持仓市值 <= 总资金 × 30%

3. 总仓位限制
   - 所有持仓总市值 <= 总资金 × 80%（保留 20% 现金）

4. 交易频率限制
   - 单日交易次数 <= 20 次（防止过度交易）
   - 同一标的 60 秒内不重复下单（防止信号重复）

5. 市场状态检查
   - 交易时段检查（盘前盘后不下单）
   - 停牌股票拒绝下单
```

##### 风控检查流程
```
策略生成交易信号
    ↓
风控引擎检查
    ├─ 通过 → 提交订单
    └─ 拒绝 → 记录拒绝原因 + 告警
```

##### 验收标准
- ✅ 所有风控规则单元测试覆盖 100%
- ✅ 超限订单拦截率 100%
- ✅ 风控拒绝有日志记录

##### MVP 边界（不做）
- ❌ 复杂的风险模型（VaR、CVaR）
- ❌ 实时夏普比率监控
- ❌ 多账户风控
- ❌ 动态调整限额（根据市场波动）

##### 关键原则
- **默认拒绝**：采用白名单思维，不确定的情况默认拒绝
- **可配置**：所有风控参数（30%、80%、20 次）可通过配置文件调整

#### 模块 5：日志系统（Logging System）
**优先级**：P0  
**时间估算**：3-5 天

##### 核心功能
- ✅ 结构化日志（JSON 格式）
- ✅ 分级日志
  - `DEBUG` - 调试信息（仅开发环境）
  - `INFO` - 常规信息（策略信号、订单提交）
  - `WARNING` - 警告信息（风控拒绝、数据延迟）
  - `ERROR` - 错误信息（API 调用失败、数据库异常）
  - `CRITICAL` - 严重错误（系统崩溃、连接断开）
- ✅ 关键操作记录
  - 订单生成、提交、成交、撤单
  - 持仓变化
  - 风控拒绝
  - 系统启动、停止
- ✅ 日志文件按日切割

##### 日志格式示例
```json
{
  "timestamp": "2026-08-14T09:30:05.123Z",
  "level": "INFO",
  "module": "strategy_engine",
  "message": "Strategy signal generated",
  "data": {
    "strategy": "MA_Cross",
    "symbol": "AAPL",
    "signal": "BUY",
    "quantity": 100,
    "reason": "MA5 cross above MA20"
  }
}
```

##### 验收标准
- ✅ 所有关键操作可追溯
- ✅ 错误日志及时记录
- ✅ 日志文件不会无限增长（定期清理）

##### MVP 边界（不做）
- ❌ 日志分析平台（ELK、Grafana）
- ❌ 实时日志监控大屏
- ❌ 日志压缩归档自动化
- ❌ 分布式日志收集

##### 关键实现
```python
import logging
import json

class StructuredLogger:
    def info(self, message, **kwargs):
        log_entry = {
            "timestamp": datetime.now().isoformat(),
            "level": "INFO",
            "message": message,
            "data": kwargs
        }
        logging.info(json.dumps(log_entry))
```

#### 模块 6：实盘交易引擎（Live Trading Engine）
**优先级**：P0  
**时间估算**：1-2 周

##### 核心功能
- ✅ 实时行情推送处理

  ```
  连接断开检测
      ↓
  停止新订单提交
      ↓

      ├─ 尝试 1: 立即重连
  ```

#### 模块 7：订单管理系统（OMS）
**优先级**：P0  
**时间估算**：1-2 周

##### 核心功能
- ✅ 订单提交到 IBKR
- ✅ 订单状态跟踪
  ```
  [创建订单]
      ↓
  [提交到券商] → PreSubmitted
      ↓
  [券商确认] → Submitted
      ↓
  [开始成交] → PartiallyFilled
      ↓
  [全部成交] → Filled
  
  [取消路径] → Cancelling → Cancelled
  [拒绝路径] → Rejected
  ```
- ✅ 订单幂等性（防止重复下单）
  ```python
  order_id = f"{strategy_id}_{symbol}_{timestamp}_{signal_hash}"
  
  # 60 秒内相同信号去重
  if redis.exists(f"order_lock:{order_id}"):
      return "订单已存在，跳过"
      
  redis.setex(f"order_lock:{order_id}", 60, "1")
  ```
- ✅ 订单超时处理
  - 限价单 30 秒未成交 → 撤单 → 价格追踪重发（最多 3 次）
  - 市价单直接提交，接受滑点

##### 订单类型支持（MVP）
- ✅ 市价单（Market）
- ✅ 限价单（Limit）
- ❌ 止损单、止盈单、条件单（第二版）

##### 验收标准
- ✅ 手动下单 100 次，订单状态准确率 100%
- ✅ 无重复下单事故
- ✅ 订单超时自动处理

##### MVP 边界（不做）
- ❌ 算法单（TWAP、VWAP、冰山单）
- ❌ 条件单（如触及价格后下单）
- ❌ 订单拆分（大单拆分成多个小单）

#### 模块 8：仓位管理系统（PMS）
**优先级**：P0  
**时间估算**：1 周

##### 核心功能
- ✅ 实时持仓更新
  - 订单成交后立即更新本地持仓
  - 维护持仓数量、成本价、市值
- ✅ 盈亏计算
  ```python
  # 浮动盈亏（未实现盈亏）
  unrealized_pnl = (current_price - cost_price) × quantity
  
  # 已实现盈亏
  realized_pnl = (sell_price - cost_price) × sold_quantity
  
  # 日内盈亏
  daily_pnl = today_realized_pnl + sum(unrealized_pnl)
  ```
- ✅ 持仓对账（每 5 分钟与 IBKR 对账）
  ```
  定时任务（每 5 分钟）
      ↓
  从 IBKR 拉取持仓快照
      ↓
  对比本地持仓记录
      ↓
  差异检测
      ├─ 差异 < 1 股 → 正常（四舍五入误差）
      └─ 差异 >= 1 股 → 告警 → 以 IBKR 为准更新本地
  ```
- ✅ 可用资金计算
  ```python
  available_cash = total_cash - frozen_cash - sum(position_value)
  ```

##### 验收标准
- ✅ 持仓计算准确率 100%
- ✅ 对账差异及时发现并告警
- ✅ 盈亏计算正确

##### MVP 边界（不做）
- ❌ 复杂的绩效归因（收益分解到选股、择时、行业）
- ❌ 多账户合并持仓
- ❌ 历史持仓分析和可视化
- ❌ 持仓优化建议

##### 关键原则
- **权威数据源**：IBKR 账户数据为权威源，本地维护副本

#### 模块 10：完善风控
**优先级**：P0  
**时间估算**：1 周

##### 核心功能：持续监控（运行时）

```python
# 风控规则（运行时持续检查）
1. 止损监控
   - 单票持仓亏损 >= 设定止损比例（如 -5%）→ 自动平仓
   - 当日总亏损 >= 2% → 停止所有开仓，只允许平仓

2. 止盈监控
   - 单票持仓盈利 >= 设定止盈比例（如 +10%）→ 自动平仓
   - （可选）移动止盈（追踪止损）

3. 回撤监控
   - 记录最高净值
   - 当前净值 / 最高净值 - 1 = 当前回撤
   - 回撤 >= 5% → 告警
   - 回撤 >= 10% → 停止开仓

4. 持仓时间监控
   - 单票持仓超过 N 天 → 提醒复核
```

##### 风控触发流程
```
定时任务（每 10 秒检查一次）
    ↓
遍历所有持仓
    ↓
计算浮动盈亏
    ↓
检查止损/止盈条件
    ↓
触发条件
    ├─ 生成平仓信号
    ├─ 提交平仓订单
    ├─ 记录日志
    └─ 发送告警
```

##### 验收标准
- ✅ 止损触发准确（延迟 < 30 秒）
- ✅ 止盈触发准确
- ✅ 亏损限制生效（达到 2% 停止开仓）
- ✅ 所有风控动作有日志和告警

##### MVP 边界（不做）
- ❌ 复杂的风险模型（VaR、夏普比率实时监控）
- ❌ 动态止损（如追踪止损、ATR 止损）
- ❌ 组合级风险控制（Beta 对冲、行业中性）
- ❌ 压力测试和情景分析

##### 关键实现
```python
class RiskMonitor:
    def check_stop_loss(self, position):
        """检查止损"""
        pnl_pct = position.unrealized_pnl / position.cost
        if pnl_pct <= -0.05:  # -5% 止损
            self.log_warning(f"Stop loss triggered: {position.symbol}")
            self.close_position(position)
            self.send_alert("CRITICAL", f"Stop loss: {position.symbol}")
```

- 高频 Tick 级交易（延迟要求极高）
- 机器学习模型训练（复杂度高）
- 分布式架构（单机够用）
- 多账户管理（个人交易不需要）
- 复杂的绩效归因（第二版再考虑）

## 五、关键成功因素

### 1. 聚焦核心路径
**数据 → 策略 → 风控 → 下单 → 跟踪**

不被边缘功能分散精力：
- ❌ 不做漂亮的 UI（命令行够用）
- ❌ 不做多余的数据源（一个稳定的即可）
- ❌ 不做复杂的因子（简单技术指标即可）

### 2. 风控优先
**宁可少做功能，风控必须到位**

- ✅ 所有风控规则必须有单元测试
- ✅ 风控拒绝必须有日志和告警
- ✅ 止损必须自动触发，不依赖人工

### 3. 充分测试
**关键路径必须严格测试**

- 订单幂等性（防止重复下单）
- 状态同步（本地持仓与券商一致）
- 异常恢复（断线重连、订单恢复）
- 风控有效性（超限必须拦截）

### 4. 逐步上线
**不要一步到位直接实盘**

```
回测验证（1-2 周）
    ↓
模拟盘验证（2-4 周）
    ↓
小资金实盘（1000 元级别，2 周）
    ↓
正常资金量（逐步加仓）
```

### 5. 避免过度设计
**够用就行，不追求完美**

- 初期命令行交互足够，不需要 Web 界面
- 初期邮件告警足够，不需要短信/微信
- 初期简单回测足够，不需要复杂的参数优化

## 六、风险点与验证清单

### 高风险点（必须测试）

#### ❗ 风险 1：重复下单
**场景**：网络重试导致同一信号下单 2 次  
**防护**：订单幂等性（唯一 ID + 60 秒内去重）  
**验证方法**：
```python
# 模拟网络抖动测试
def test_duplicate_order():
    signal = generate_signal()
    
    # 快速提交两次相同信号
    order1 = submit_order(signal)
    order2 = submit_order(signal)  # 应该被拦截
    
    assert order2 is None, "重复订单未拦截！"
```

---

#### ❗ 风险 2：状态不同步
**场景**：本地持仓与 IBKR 账户不一致  
**防护**：定期对账 + 差异告警  
**验证方法**：
```python
# 手动修改 IBKR 持仓，确认系统发现并告警
def test_position_sync():
    # 本地记录：持仓 100 股
    local_position = 100
    
    # 模拟券商持仓变化（手动平仓 10 股）
    ibkr_position = 90
    
    # 触发对账
    run_reconciliation()
    
    # 验证：应该发现差异并告警
    assert check_alert_sent("position_mismatch")
```

---

#### ❗ 风险 3：风控失效
**场景**：风控检查被绕过或计算错误  
**防护**：单元测试覆盖所有风控规则  
**验证方法**：
```python
# 构造超限场景，确认被拒绝
def test_risk_control():
    # 持仓已达 80%
    current_position_ratio = 0.80
    
    # 尝试再开仓 10%（超过 80% 限制）
    order = create_buy_order(amount_ratio=0.10)
    result = risk_check(order)
    
    assert result.rejected, "风控未拦截超限订单！"
    assert "仓位限制" in result.reason
```

---

#### ❗ 风险 4：断线未恢复
**场景**：系统以为在运行但实际未连接  
**防护**：心跳检测 + 连接状态监控  
**验证方法**：
```python
# 断开连接，确认 1 分钟内告警
def test_connection_lost():
    # 模拟连接断开
    disconnect_broker()
    
    # 等待 60 秒
    time.sleep(60)
    
    # 验证：应该收到告警
    assert check_alert_sent("connection_lost")
```

---

### 验收标准清单

| 验收项 | 标准 | 验证方法 |
|-------|------|---------|
| 数据稳定性 | 24 小时不断线 | 长稳测试 |
| 订单准确性 | 100 次下单状态 100% 准确 | 压力测试 |
| 风控有效性 | 超限订单拦截率 100% | 单元测试 |
| 持仓一致性 | 对账差异及时发现 | 对账测试 |
| 异常恢复 | 断线重连成功率 > 95% | 异常注入测试 |
| 止损有效性 | 触发延迟 < 30 秒 | 模拟止损场景 |

## 七、常见问题

### Q1：MVP 需要多少时间？
**A**：8-12 周（2-3 个月）
- 阶段一（基础框架）：4-6 周
- 阶段二（实盘能力）：4-6 周
- 不包括模拟盘验证时间（建议至少 2-4 周）

### Q2：MVP 需要多少代码量？
**A**：预估 5,000-8,000 行 Python 代码
- 不包括配置文件、测试代码、文档

### Q3：必须使用 PostgreSQL 和 Redis 吗？
**A**：不是必须，但强烈建议
- PostgreSQL 可替换为 MySQL、SQLite（开发阶段）
- Redis 可替换为内存缓存（功能受限）

### Q4：必须对接 IBKR 吗？
**A**：不是必须，但 IBKR 是个人交易者的好选择
- 支持全球市场
- API 成熟稳定
- 可替换为其他券商（需要实现相应接口）

### Q5：MVP 可以跳过回测引擎吗？
**A**：强烈不建议
- 回测是策略验证的唯一方式
- 没有回测直接实盘风险极高

### Q6：如何避免过度工程化？
**A**：遵循"能用就行"原则
- 每个功能都问自己：不做会死吗？
- 如果答案是"不会"，那就第二版再做
- MVP 的目标是"能跑"，不是"完美"
